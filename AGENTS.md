# AGENTS.md — правила разработки `interlink-front`

Единственный источник правил для разработчиков и AI-агентов.
`CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.cursor/rules/`, `.windsurf/rules/` — тонкие указатели на этот файл.

**Приоритет источников при конфликте:** явная просьба пользователя → этот файл → `docs/PERFORMANCE.md` (детали по производительности) → существующий код рядом с правкой.

---

## 1. Проект

Внутренний корпоративный портал: корреспонденция (внешняя/внутренняя), задачи, HR, администрирование, профиль, чат. Язык интерфейса и документации — русский.

**Стек (проверено по `package.json`):** React 19 · TypeScript 5.9 (strict) · Vite 7 + SWC · TanStack Query **v4** · Ant Design 6 · Tailwind CSS 4 · react-router 7 · axios · framer-motion · lucide-react · CKEditor 5 · recharts · dayjs. Архитектура — **Feature-Sliced Design**.

Бэкенд — **Laravel**, отдельный репозиторий. Здесь только фронтенд.

Критичные для агентов особенности версий:

- **TanStack Query v4, не v5.** Используем `cacheTime` (не `gcTime`), `keepPreviousData: true` (не `placeholderData: keepPreviousData`), `useQuery({...})` v4-семантику `isLoading`. Код из v5-примеров не компилируется.
- **React Compiler не подключён** (несовместим с SWC-плагином) — `useMemo` / `useCallback` / `React.memo` расставляем вручную там, где это обосновано.
- **Tailwind v4** подключён плагином `@tailwindcss/vite`; `tailwind.config.cjs` минимальный, тема живёт в CSS.

## 2. Команды

```bash
npm run dev       # дев-сервер (порт 5173)
npm run build     # tsc -b && vite build — единственная реальная проверка типов
npm run preview   # предпросмотр прод-сборки
npm run test      # node --test: тесты на встроенном раннере Node, без зависимостей
```

Тестового фреймворка (Vitest/Jest) и DOM-окружения (jsdom) в проекте **нет** и без согласования не появляется. Тесты в `tests/` работают на встроенном раннере Node (`node --test`) и покрывают то, что проверяется без DOM: чистые функции (Node сам снимает типы с `.ts`), синтаксис исходников и инварианты оформления документа. Логику, которой нужен настоящий DOM или раскладка страницы, тестами не покрыть — её проверяет пользователь в браузере.

ESLint настроен, но в сборку не входит и командой не обеспечен: ориентир качества — `tsc`, а не lint.

**Запуск сборки, проверку типов и браузерное/визуальное тестирование выполняем только по явной просьбе пользователя** (см. §17).

## 3. Архитектура FSD

Слои сверху вниз. Импорт разрешён **только вниз**, никогда вверх и никогда вбок между модулями одного слоя:

```
app → pages → widgets → features → entities → shared
```

| Слой | Ответственность | Запрещено |
|---|---|---|
| `app/` | Бутстрап, провайдеры (`QueryClientProvider`, antd `ConfigProvider`, `ErrorBoundary`), роутинг, глобальные стили | Бизнес-логика, разметка экранов |
| `pages/` | Тонкая точка монтирования роута: собрать layout, прокинуть параметры, отрендерить виджет/фичу | Запросы к API, бизнес-правила, тяжёлый JSX |
| `widgets/` | Оркестраторы экрана: владеют серверными данными и главным состоянием, обрабатывают загрузку/ошибки, раскладывают фичи | Вызов **внутренних** подкомпонентов чужих фич |
| `features/` | Законченный пользовательский сценарий: форма, модалка, фильтр, карточка действия | Импорт из `widgets` и `pages` |
| `entities/` | Доменные типы и мелкие переиспользуемые представления сущности | Любые импорты выше `shared` |
| `shared/` | Инфраструктура: `api/`, `config/`, `lib/`, `ui/`, `types/` | Любая доменная логика и импорты из верхних слоёв |

**Псевдонимы путей** (`tsconfig.json` + `vite.config.ts`): `@app/*`, `@pages/*`, `@widgets/*`, `@features/*`, `@entities/*`, `@shared/*`. Относительные пути — только внутри одного модуля.

**Публичный API модуля.** Наружу модуль виден через свой `index.ts`. Импорт из чужого модуля идёт на корень (`@widgets/NewRegistry`), а не вглубь (`@widgets/NewRegistry/ui/RegistryLayout`). Внутри модуля глубокие пути нормальны.

**Поток данных — вниз через пропсы.** Данные грузит владелец экрана (обычно виджет) и передаёт фичам пропсами. Фича вправе владеть своими данными сама, если сценарий самодостаточен (собственная модалка, независимый список, свой мутационный поток) — тогда запросы выносятся в `api/` или хук `useXxxData` внутри фичи, а не размазываются по JSX. Одни и те же данные не тянем дважды с разных уровней.

**Слабая связанность.** Модуль общается с внешним миром только через пропсы и колбэки. Никаких обращений к внутренностям соседа, никакого «пробрасывания» стора соседнего модуля. Общее — поднимается в `shared` или `entities`.

## 4. Структура модуля

```
ModuleName/
  index.ts        # публичный API: только то, что нужно снаружи
  ui.tsx          # главный компонент (или ModuleName.tsx — обе формы в проекте есть, следуй соседям)
  ui/             # подкомпоненты, каждый в своём файле
  model.ts        # типы, константы, схемы валидации, доменные enum'ы
  lib.ts | lib/   # чистые функции, хелперы, columns таблиц, хуки модуля
  api/            # запросы и хуки данных модуля (если их больше пары)
  style.css       # локальные стили модуля (при необходимости)
```

`columns` для таблиц объявляем на уровне модуля или мемоизируем — но **не** пересоздаём в теле компонента каждый рендер.

## 5. Лимит размера файла — 250 строк

**Целевой предел: ~250 строк на любой файл** (`.ts`, `.tsx`, `.css`). 250 — не жёсткий обрыв на 251-й строке, а порог, после которого нужно осознанно решить: декомпозировать сейчас или зафиксировать причину.

- **до 250** — норма, ничего не требуется;
- **250–400** — жёлтая зона: декомпозируй, если правишь этот файл по задаче;
- **свыше 400** — красная зона: новый код такого размера не принимается.

Порог считаем по строкам файла целиком, включая типы и импорты.

**Исключение — файлы-данные.** Лимит не применяется к файлам, состоящим из данных без логики: словари переводов, справочники констант, токены темы, наборы типов, реестры маршрутов (`ApiRoutes`, `AppRoutes`). Дробить их вредно — теряется единая точка поиска, а выигрыша в читаемости нет. Такой файл делим только по доменному признаку и только когда он реально мешает (например, типы разных сущностей в одном `model.ts`).

### Как декомпозировать (по приоритету)

1. **Подкомпоненты.** Самостоятельный кусок JSX с собственным смыслом (шапка, строка списка, панель действий, футер модалки) → отдельный файл в `ui/`. Признак: у куска есть имя, которое произносишь вслух.
2. **Хуки.** Связка `useState` + `useEffect` + производные значения вокруг одной темы → `useSomething()` в `lib/`. Хук возвращает данные и обработчики, компонент остаётся про разметку.
3. **Данные.** Запросы, мутации, инвалидация, нормализация ответа → `api/useXxxData.ts`. Компонент не должен знать формат ответа бэкенда.
4. **Чистые функции.** Форматирование, сортировка, фильтрация, маппинг, вычисление статусов → `lib.ts`. Их легко читать и переиспользовать.
5. **Типы и константы.** Интерфейсы, справочники, дефолты, тексты статусов → `model.ts`.
6. **Конфигурация вместо разметки.** Однотипные поля формы, колонки, вкладки, пункты меню → массив-описание + рендер в цикле. Пятнадцать похожих `<Input>` подряд — это данные, а не код.

### Чего делать нельзя

- Резать файл механически на `part1.tsx` / `part2.tsx` ради счётчика строк — куски должны иметь смысл и имя.
- Создавать «файл-мешок» `helpers.ts` со всем подряд.
- Разносить состояние по подкомпонентам так, что родитель перестаёт понимать экран: состояние живёт у владельца, вниз идут значения и колбэки.

### Существующие большие файлы

В репозитории есть файлы на 700–7000 строк (§20). Они — легаси, а не образец. Правило: **точечная правка большого файла не обязана превращаться в его переписывание**. Разбиваем ту часть, которую действительно трогаем, и оставляем остальное. Массовый рефакторинг таких файлов — отдельная согласованная задача.

## 6. Именование

- **Компоненты** — `PascalCase`, файл называется как компонент (`UserProfileModal.tsx`), либо `ui.tsx` для главного компонента модуля.
- **Хуки** — `useCamelCase`, один хук на файл.
- **Функции, переменные** — `camelCase`; **константы-справочники** — `UPPER_SNAKE_CASE`.
- **Интерфейсы** — префикс `I` (`IProps`, `IUser`, `ICurrentUserPermissions`). Локальные пропсы компонента — `IProps`; экспортируемые — осмысленное имя.
- **Type-алиасы** — префикс `T` (`TTabMode`, `TMenuItem`).
- **Булевы значения** — `is…`, `has…`, `can…`, `should…`.
- **Обработчики** — `handleXxx` внутри компонента, `onXxx` в пропсах.
- **Файлы CSS/директории** — как соседи в том же слое; новые латиницей и без опечаток.
- **CSS-классы — стандартный БЭМ:** `block__element--modifier` (в проекте: `.ui-tab`, `.ui-tab--active`). Блок префиксуем зоной ответственности (`ui-`, имя модуля), чтобы не пересекаться с antd и Tailwind.

## 7. TypeScript

- `strict: true` включён — не обходим его через `@ts-ignore`, `as any`, `!` на пустом месте.
- **Новый код без `any`.** Не знаешь тип — `unknown` + сужение, либо опиши интерфейс ответа. В старом коде `any` много; трогаешь строку — типизируй её, но не начинай сплошную типизацию файла без задачи.
- Типы ответов API описываем рядом с запросом или в `model.ts` модуля; общие доменные типы — в `entities/*/model.ts`.
- Union'ы вместо «магических» строк: `type TKind = "incoming" | "outgoing"`.
- `enum` не обязателен — `as const`-объект предпочтительнее (так сделаны `AppRoutes` / `ApiRoutes`).
- Никаких «магических» строк и чисел в логике: статусы, лимиты, ключи `localStorage`, тексты — в `model.ts` модуля или `shared/config`.

## 8. React: компоненты и хуки

- **Компоненты — стрелочные функции с именованным экспортом.** `React.FC` в новом коде не нужен: типизируем пропсы напрямую (`({ a, b }: IProps) =>`). Существующие `React.FC` не переписываем без причины.
- **Guard-clause разрешён и приветствуется:** ранний `return null` / скелетон / пустое состояние в начале функции читается лучше, чем тройной тернарник в JSX. Запрещены вложенные тернарники глубже одного уровня.
- **Условный рендер блоков — `<If is={...}>` из `@shared/ui`** (проп называется `is`, не `condition`). Для коротких инлайновых случаев (иконка, класс, атрибут) допустимы `&&` и тернарник — плодить `If` вокруг одного символа не надо.
- **Правила хуков соблюдаем строго:** только на верхнем уровне, честные зависимости, никаких условных вызовов. `useEffect` — для синхронизации с внешним миром (DOM, подписки, таймеры), не для вычисления производных данных: производное считается на рендере или в `useMemo`.
- **Один компонент — одна ответственность.** Компонент, который и грузит, и фильтрует, и рисует, и печатает — это три компонента и один хук.
- **Композиция вместо флагов.** Пять булевых пропсов, переключающих режимы, — сигнал, что нужны разные компоненты или `children`/слоты.
- **Списки — стабильный `key` из данных**, не индекс массива.
- **Тяжёлые экраны и модалки — `React.lazy` + `<Suspense>`** (как в `app/routes/AppRouter.tsx`).

## 9. Данные и API

**Единственные точки входа:** `useGetQuery` (чтение) и `useMutationQuery` (запись) из `@shared/lib`. Прямой `axios`/`_axios` в компонентах — только для нестандартных случаев вроде скачивания файла с `responseType: "blob"`.

```ts
const { data, isLoading, refetch } = useGetQuery<IParams, IApiResponse<IUser>>({
  url: ApiRoutes.AUTH_ME,
  params,
  useToken: true,
  options: { staleTime: 5 * 60 * 1000 },
});

const { mutate } = useMutationQuery({
  url: ApiRoutes.CREATE_FOLDER,
  method: "POST",
  messages: {
    success: "Папка создана",
    invalidate: [ApiRoutes.GET_FOLDERS],
  },
});
```

- **URL — только из `ApiRoutes`** (`@shared/api/api-routes.ts`), маршруты UI — только из `AppRoutes` (`@shared/config/AppRoutes.ts`). Хардкод строк пути запрещён.
- **Реальное соглашение бэкенда — REST с версией:** `/api/v1/<resource>`, `/api/v1/<resource>/:id`, вложенные действия — `/api/v1/<resource>/:id/<action>`. Новые эндпоинты добавляем в этом же стиле.
- **Ключи кэша** `useGetQuery` собирает сам: `[url, params, useToken]`. Поэтому инвалидация всегда идёт по константе из `ApiRoutes`, а не по произвольной строке. Наборы связанных ключей — в `shared/config` (пример: `CORRESPONDENCE_INVALIDATE_KEYS`).
- **Мутация обязана инвалидировать затронутые ключи** — точечно, а не `queryClient.clear()`.
- **Тосты по умолчанию автоматические:** `useMutationQuery` сам показывает успех/ошибку. Свой `toast` поверх — дубль; глушится через `messages.suppressSuccessToast`.
- **Контракт ответа Laravel:** `{ success: boolean; message: string; data: T }`. Пагинация: `{ current_page, data, last_page, per_page, total }`. Читаем через опциональные цепочки — часть ручек отдаёт `data` напрямую.
- **Файлы:** собираем `buildFormData()` из `@shared/lib` (bracket-нотация, Laravel-совместимая) и шлём **POST с `_method: "PUT" | "PATCH"`** — PHP не разбирает файлы в теле настоящих PUT/PATCH.
- `staleTime` задаём осознанно; глобальные дефолты — в `shared/lib/queryClient.ts` (`retry: 0`, `staleTime: 5 мин`, без refetch на фокус).

## 10. Состояние

Библиотек глобального состояния (Zustand/Redux/Jotai) в проекте **нет** — не добавляй их без явного согласования. Порядок выбора:

1. **Серверные данные — TanStack Query.** Не копируем ответ в `useState`: кэш и есть источник правды.
2. **Локальное состояние — `useState`/`useReducer`** в ближайшем общем владельце.
3. **Состояние экрана в URL** — фильтры, вкладки, страница пагинации через `useDynamicSearchParams` (`@shared/lib`): так состояние переживает F5 и делится ссылкой.
4. **React Context** — только для по-настоящему сквозного (пример: `ChatProvider`). Контекст со всем подряд — источник лишних ререндеров.

`localStorage` используем точечно и через именованные константы ключей.

## 11. UI и стилизация

- **Tailwind — основной инструмент стилизации.** Локальные `style.css` внутри модуля — для того, что классами выражается плохо (сложные селекторы, переопределение antd, анимации ключевыми кадрами). Глобальное — только `app/styles/global.css`.
- **`!important` в Tailwind v4 — постфиксом:** `flex!`, `bg-red-500!`. Префиксная форма `!flex` не работает.
- **Inline `style={{}}`** допустим для **вычисляемых** значений (проценты, `transform`, цвет из данных). Статическое оформление — классами.
- **Тёмная тема** — класс `.dark` на `<html>`, в разметке `dark:`-варианты Tailwind. Для antd-поддеревьев — `useIsDarkMode()` + `theme.darkAlgorithm` в `ConfigProvider`.
- **Иконки** — `lucide-react` (основной набор). `@ant-design/icons` — там, где иконка живёт внутри antd-компонента.
- **Анимации** — `framer-motion` либо CSS-переходы; анимируем `transform`/`opacity`, уважаем `prefers-reduced-motion`.
- **`cn()` из `@shared/lib` — простая склейка классов**, а не `tailwind-merge`: конфликтующие утилиты она **не** разрешает. Не полагайся на «последний класс победит».
- **Тултипы** — `<Tooltip>` из `@shared/ui`. Нативный атрибут `title` на DOM-элементах не используем (проп `title` у antd-компонентов — это другое, он разрешён).
- **Действия в таблицах** — иконочные кнопки (`type="text"`) в `<Tooltip>`, без текстовых подписей.
- **Ховер интерактивных карточек** — фон, граница, тень. Сдвиг по вертикали (`translateY`) не используем.
- **Адаптивность** — mobile-first, flex/grid.
- **Доступность** — `aria-label` на иконочных кнопках, видимый фокус, работа с клавиатуры в модалках.

## 12. UI-библиотеки: правило неприкосновенности

Проект **не обязывает** использовать какую-либо UI-библиотеку. Ant Design используется исторически и широко (~137 файлов); часть экранов написана на чистом Tailwind + lucide + framer-motion. Оба подхода легитимны.

**Жёсткие правила:**

1. **Массовая замена компонентов ради смены библиотеки запрещена.** Не переписываем antd на Tailwind (и наоборот), если задача — не миграция.
2. **Правишь существующий функционал — сохраняешь его текущую библиотеку и структуру.** Работа идёт в том стиле, в котором написан файл.
3. **Новый изолированный модуль** пишется в стиле соседей по разделу; выбор в спорном случае — за автором, а не за этим документом.
4. **Новые UI-зависимости (MUI, shadcn/ui, Chakra, Mantine и пр.) не добавляем** без явного согласования — это фрагментирует бандл и дизайн.
5. Смена библиотеки — только как **отдельная задача с явной постановкой**.

## 13. Права доступа

- `useCurrentUser()` (`@shared/lib`) — текущий пользователь и effective-права из `auth/me`: `hasPermission`, `hasAnyPermission`, `hasAllPermissions`, `hasRole`.
- `<Can permission="...">` (`@shared/ui`) — гейтинг UI-элемента; `fallback` — что показать без прав.
- `useGetQuery`/`useMutationQuery` умеют проверять права до запроса: `preload: true` + `preloadConditional: [...]`.
- **Права на клиенте — это UX, а не безопасность.** Итоговая проверка всегда на бэкенде; скрытие кнопки не заменяет серверный отказ.
- Токен — только через `tokenControl` (`@shared/lib`), напрямую к `localStorage` за токеном не ходим.

## 14. Производительность по умолчанию

Перф-правила делятся на два класса, и путать их нельзя.

**Write-time — обязательны всегда, прямо здесь.** Стоят ноль при написании и дорого стоят при исправлении задним числом. Код, написанный по этому списку, не нуждается в последующей оптимизации:

1. **Тяжёлое — лениво.** CKEditor, pdfjs, xlsx, mammoth, recharts, крупные модалки и целые экраны — `React.lazy` + `<Suspense>` или динамический `import()` в момент действия. Никогда статическим импортом в always-mounted коде.
2. **Скрытое не монтируется.** Содержимое неактивной вкладки, закрытой модалки, свёрнутой панели не рендерится вовсе, а не прячется через `display: none`.
3. **Стабильные `key`** из данных, не индекс массива.
4. **`columns`, дефолтные объекты и массивы — вне рендера:** константа модуля или `useMemo`. Пересоздание каждый рендер убивает мемоизацию таблицы.
5. **Никаких новых объектов, массивов и стрелок в пропсах мемоизированных или тяжёлых детей** — `useMemo`/`useCallback`/константа. React Compiler не подключён, за нас это никто не сделает.
6. **`React.memo` — тяжёлым детям** со стабильными пропсами. Лёгкие компоненты мемоизировать не нужно, это шум.
7. **Серверные данные — только из TanStack Query**, с осознанным `staleTime`. Не копируем ответ в `useState`, не дублируем один запрос на двух уровнях.
8. **`select`** в запросе, если компоненту нужен кусок ответа, а не весь.
9. **Мутации инвалидируют точечные ключи**, а не весь кэш.
10. **Ввод, бьющий в API или тяжёлый рендер, — через `useDebouncedCallback`**; тяжёлая фильтрация — `useDeferredValue`.
11. **Изображения:** заданы `width`/`height` или `aspect-ratio`, `loading="lazy"` (кроме LCP), осмысленный `alt`.
12. **Анимации — только `transform` и `opacity`**, с уважением к `prefers-reduced-motion`.
13. **Никаких тяжёлых синхронных вычислений** в обработчиках и на рендере.
14. **Вес новой зависимости проверяем до установки** — ESM и tree-shaking обязательны.
15. **`ErrorBoundary`** на крупных блоках, `<Suspense>` на асинхронных.

**Measure-time — по данным профайлера, не по интуиции.** Анализ бандла и разбиение чанков, виртуализация длинных списков, Web Workers, preload/fetchpriority, `content-visibility`, бюджеты и Lighthouse. Угадывать их при написании кода вредно — это преждевременная оптимизация. Свод и методика — **`docs/PERFORMANCE.md`**, трекер кампании — `docs/plans/PERFORMANCE-OPTIMIZATION-PROGRESS.md`.

Правило совместного действия: `AGENTS.md` действует всегда; `PERFORMANCE.md` авторитетен по вопросам скорости и применяется на выделенном перф-проходе или аудите. В перф-цикле приостанавливаются только §4 и §5 этого файла — переразбивать модули ради структуры там нельзя. Чем строже соблюдается write-time список, тем короче становится перф-проход: в пределе он вырождается в периодический аудит без правок.

## 15. Рефакторинг существующего кода без изменения поведения

Приведение старого модуля к §3–5 — это **поведенчески нейтральная** операция. UI, тексты, бизнес-логика, порядок и состав запросов после рефакторинга обязаны совпадать с тем, что было.

- **Разрешено:** перемещать код между файлами, извлекать подкомпоненты, хуки, чистые функции, типы и константы, переименовывать внутренние сущности, чинить импорты под публичный API модуля.
- **Запрещено в том же PR:** менять разметку и классы, переписывать условия, «заодно» чинить баги, менять параметры и порядок запросов, добавлять/убирать `memo`, `lazy`, виртуализацию, переводить компонент на другую UI-библиотеку.
- **Найденный по пути баг или дубль не чиним молча** — фиксируем в списке находок модуля и выносим отдельной задачей после рефакторинга.
- **Порядок извлечения внутри файла — от безопасного к рискованному:** типы и константы → чистые функции → подкомпоненты (перенос JSX + пропсы) → хуки. Состояние в последнюю очередь и целиком, не по частям.
- **Один модуль — одна ветка — один PR.** Диффы, где перемешаны перенос кода и правка логики, не проходят ревью.
- Протокол кампании, порядок модулей и чек-лист приёмки — `docs/plans/2026-07-30-fsd-refactor-PROGRESS.md`.

## 16. Загрузки, ошибки, пустые состояния

Каждый экран с данными обрабатывает все три состояния явно:

- **загрузка** — `Loader` или `Skeleton` из `@shared/ui`, без «прыжков» layout;
- **ошибка** — сообщение пользователю (тост от `useMutationQuery` либо блок с возможностью повтора); техническую причину — в консоль, не в интерфейс;
- **пусто** — `EmptyState` из `@shared/ui` с понятным текстом и, если уместно, действием.

Пустой экран без объяснения — баг. Тексты — на русском, в тоне интерфейса.

## 17. Комментарии и документация

- **Комментарий объясняет «почему», а не «что».** Хороший пример — `buildFormData` в `shared/lib/utils.ts`: комментарий объясняет ограничение PHP, которое из кода не видно.
- **Не пишем**: пересказ кода (`// увеличиваем счётчик`), баннеры-разделители, TODO без контекста, авторские пометки, JSDoc ради JSDoc.
- **Закомментированный код удаляем.** История есть в git.
- Публичные хуки и нетривиальные утилиты в `shared` — короткий doc-комментарий с назначением.
- Существенные изменения проектируем дизайн-документом в `docs/plans/YYYY-MM-DD-<slug>-design.md`: проблема → изменения по файлам → верификация.

## 18. Процесс и правила для AI-агентов

**Ветки и коммиты.** Работа идёт в ветках с PR в `main`. Сообщения коммитов — короткие, на русском, по существу («Добавил счётчик поручений»), без служебного шума.

**Обязательные ограничения для агентов:**

0. **Не коммитить и не пушить по своей инициативе.** Изменения остаются в рабочем каталоге — их просматривает и отправляет пользователь. `git commit`, `git push`, создание PR — только по явной просьбе в текущей сессии; разрешение, данное один раз, не переносится на следующие шаги и сессии. Закончив работу, перечислить изменённые файлы, чтобы их можно было просмотреть.
1. **Категорически запрещено самовольно запускать `npx tsc -b`, `tsc`, `npm run build` или фоновые команды проверки типов** после правок. Проверка типов или сборка запускается **ТОЛЬКО** если пользователь в текущем сообщении явно написал команду («проверь типы», «запусти tsc», «проверь сборку»).
2. **Не проводить браузерное/визуальное тестирование** и не запускать дев-сервер для проверки внешнего вида — пользователь тестирует визуал сам. Исключение — явная просьба.
3. **Не делать массовых рефакторингов** (смена UI-библиотеки, переразбиение по FSD, сплошная типизация, переформатирование) вне явно поставленной задачи.
4. **Не добавлять зависимости** без согласования.
5. **Не трогать** `src/widgets/NewProfileDesign/`, `DesignTaskCode/`, `NewDesignAccess/`, `NewChatDesign/`, `hrkm/` — это локальные дизайн-песочницы, они в `.gitignore` и исключены из сборки.
6. **Перед правкой — прочитать соседние файлы** и следовать их стилю: этот документ описывает норму, а не оправдывает переписывание чужого кода под неё.
7. **Отчитываться честно:** что сделано, что не сделано и почему; не заявлять о проверке, которая не проводилась.

## 19. Definition of Done

- [ ] Правило слоёв FSD не нарушено, импорты идут только вниз и через публичный API модуля.
- [ ] Новые файлы укладываются в ~250 строк; выросшее — декомпозировано осмысленно.
- [ ] Никаких хардкод-путей: только `ApiRoutes` / `AppRoutes`; магические значения — в константах.
- [ ] Данные — через `useGetQuery` / `useMutationQuery`; мутации инвалидируют нужные ключи.
- [ ] Обработаны загрузка, ошибка и пустое состояние.
- [ ] Нет `any` в новом коде, нет неиспользуемых импортов и переменных.
- [ ] Нет закомментированного кода и комментариев-пересказов.
- [ ] Стиль соответствует соседним файлам; библиотека компонентов не подменена.
- [ ] Write-time перф (§14) соблюдён: тяжёлое — лениво, скрытое не смонтировано, `key` из данных, `columns` вне рендера, пропсы к мемо-детям стабильны.
- [ ] Если PR — рефакторинг (§15): UI, тексты, запросы и логика не изменились, диff состоит из перемещений.
- [ ] Иконочные кнопки имеют `aria-label`/`Tooltip`.
